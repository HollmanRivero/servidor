        HTTP 401 "Your api key: ****f909 is invalid"   <-- previous key, now fixed

Two DeepSeek behaviours worth knowing before changing anything:
  a) `deepseek-flash` is a REASONING model. `reasoning_tokens` are billed
     against `max_tokens`. With max_tokens=20 the entire budget was eaten by
     thinking and the response was:
         finish_reason = "length", content = '' (empty), reasoning_tokens = 20
     With max_tokens=4096 there is plenty of headroom, so it works today.
     If anyone lowers max_tokens, replies silently become EMPTY.
  b) With an agent-flavoured system prompt and no `tools` parameter,
     deepseek-flash returns its tool-call markup as plain text content:
         <|DSML| calls> <|DSML| invoke name="bash"> ...
     `_ask_deepseek()` in main.py:819 sends NO tools, so this markup can leak
     into normal chat replies. Mitigated only by the system prompt wording.


6. ROOT CAUSES IN CODE (ranked by impact)
------------------------------------------------------------------------------
All references are to backend/main.py.

RC0 (biggest, and not a code bug) - the running process predates the .env
    edit, so the new DeepSeek key was never loaded. See section 0.
    main.py:42   load_dotenv(BASE_DIR / ".env", override=True)   <-- runs once
    main.py:55   DEEPSEEK_API_KEY = os.environ.get(...)          <-- frozen
    main.py:84   DEEPSEEK_MODEL   = os.environ.get(...)          <-- frozen

RC1 (main cause) - the model list is ordered by "newest first", and the newest
model is the one that is overloaded.
    main.py:86  GEMINI_MODELS order starts with gemini-3.8-flash
    main.py:757 for model in _gemini_model_order(): ...
    gemini-3.8-flash returns 503 as measured above, so every request pays a
    ~6-7s failure before reaching a model that works.

RC2 - `gemini-flash-latest` hangs and eats the full timeout.
    main.py:765  _post_json(url, payload, timeout=35)
    Measured: >45s without answering. A hang is not an HTTPError, so it falls
    into `except Exception` (main.py:789) and moves to the next model - correct
    behaviour, but it costs the full 35s each time it is reached. If the models
    before it also fail, one user question can take 60-90s and the client shows
    it as "the API is not working".

RC3 - 503/429 is retried on the SAME model before moving on.
    main.py:81   TRANSIENT_RETRY_STATUS = {408, 429, 500, 502, 503, 504}
    main.py:782  if e.code in TRANSIENT_RETRY_STATUS and attempt == 0:
    main.py:784  time.sleep(1.2)  -> retries the overloaded model
    For a "high demand" 503 a retry of the same model has no value; the next
    model is strictly better. This adds ~7s and usually fails again.

RC4 - `_gemini_last_good` pins a model that may have become overloaded.
    main.py:77   _gemini_last_good
    main.py:729  _gemini_model_order(): puts _gemini_last_good FIRST
    The "sticky good model" is never invalidated. Once a model is overloaded,
    every new request starts by failing on it. Also the `"lite" not in
    _gemini_last_good` check is a plain substring match - fragile and
    undocumented.

RC5 - Gemini 3 thinking models run unbounded.
    main.py:744  generationConfig = {"temperature": ..., "maxOutputTokens": 8192}
    No `thinkingConfig.thinkingBudget` is set. `thoughtsTokenCount` was already
    94 for a one-word prompt. On real prompts this inflates latency and feeds
    RC2's timeouts. Setting a thinking budget (or 0 for chat) is the cheapest
    latency win.

RC6 - the user-facing error is misleading when the key is wrong.
    main.py:816  raise RuntimeError("Ingen Gemini-modell svarte. " + problems)
    A 401/403 on every model is reported as "no model answered", which sends
    you looking for a network problem instead of a key problem. The 401 above
    ("ACCESS_TOKEN_TYPE_UNSUPPORTED") proves how confusing this gets.

RC7 (housekeeping) - backend/.env contains a duplicate typo entry:
    GEMINI_API_KEY=...       <-- used by the code
    GEMINI_APY_KEY=...       <-- typo, never read by anything
    Delete the typo, otherwise someone will "update the key" in the wrong line
    and be back to intermittent 401s. This is very likely what happened before.

RC8 (housekeeping) - settings are defined twice and can drift:
    backend/config.py:19,35 and backend/main.py:55,84 each read
    DEEPSEEK_API_KEY / DEEPSEEK_MODEL / TECH_AI_* independently. Today they
    agree, but they are two sources of truth. main.py also loads .env with
    `override=True` (main.py:42) while config.py does not (config.py:12), so a
    variable already exported in the shell is silently replaced in one of them
    and not the other.

    large latency drop. Note: the code already has a defensive path that
    retries without responseMimeType on HTTP 400 (main.py:771); extend that
    same pattern so an unsupported thinkingConfig is dropped instead of failing
    the request.
    -> main.py:744-749

F6  Separate "auth error" from "provider busy" in the message the user sees.
    If every model returns 401/403, say the key is invalid.
    -> main.py:816, main.py:938-947

F7  Remove the GEMINI_APY_KEY typo from backend/.env, and (optionally) make

F8  Consider adding `tools=[]` or a guard in _ask_deepseek so the <|DSML|>
